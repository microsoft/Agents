# A2A In-Task Authorization Extension

Version: 1.0

Status: Provisional

Extension URI:
`https://schemas.microsoft.com/agents/a2a/extensions/in-task-authorization/v1`

## Abstract

This extension defines an in-band mechanism for resolving an A2A Task in
`TASK_STATE_AUTH_REQUIRED`. It allows an A2A Server to describe an OAuth 2.0
authorization request in a Task status message and allows an A2A Client to
deliver the resulting credential through a task-bound `resumeAuth` operation.

The extension does not replace authentication of the A2A endpoint. The
credential used to authenticate the A2A Client to the server remains in the
standard `Authorization` header. The credential procured for the interrupted
Task is carried separately in the `A2A-InTask-Authorization` header.

## Requirements language

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHALL**, **SHALL NOT**,
**SHOULD**, **SHOULD NOT**, **RECOMMENDED**, **MAY**, and **OPTIONAL** in this
document are to be interpreted as described in
[RFC 2119](https://www.rfc-editor.org/rfc/rfc2119).

## Terminology

**Authorization request**
> A server-generated request for a credential needed to continue one
> interrupted Task operation.

**Authorization request ID**
> A cryptographically random, single-use identifier that correlates an
> auth-required Task status with a subsequent `resumeAuth` request.

**Endpoint credential**
> The credential in the standard `Authorization` header used to authenticate
> the A2A Client to the A2A Server.

**In-task credential**
> The credential in the `A2A-InTask-Authorization` header that the agent needs
> to continue the interrupted operation.

## Scope

This version of the extension supports OAuth 2.0 bearer credentials. It
defines:

- Agent Card declaration and request activation.
- The metadata included in a `TASK_STATE_AUTH_REQUIRED` status message.
- JSON-RPC and HTTP/JSON forms of the `resumeAuth` operation.
- Correlation, single-use, and credential-scope requirements.

This extension does not define:

- How the A2A endpoint authenticates clients.
- How OAuth clients are registered with an authorization server.
- Credential storage or refresh beyond the interrupted operation.
- Authorization mechanisms other than OAuth 2.0 bearer credentials.

## Extension declaration

An A2A Server supporting this extension MUST include an `AgentExtension` in
`AgentCard.capabilities.extensions`.

```json
{
  "uri": "https://schemas.microsoft.com/agents/a2a/extensions/in-task-authorization/v1",
  "description": "Resolves task-scoped OAuth authorization requests.",
  "required": false,
  "params": {
    "operations": {
      "jsonRpc": "resumeAuth",
      "httpJson": "POST /tasks/{taskId}:resumeAuth"
    },
    "credentialHeader": "A2A-InTask-Authorization"
  }
}
```

The extension is OPTIONAL at the Agent Card level in version 1.0. An agent can
therefore expose skills that do not require in-task authorization to clients
that do not implement this extension.

An A2A Server MAY mark the extension as required if every supported interaction
depends on this extension. Version 1.0 does not define conditional Agent Card
extension requirements.

The extension declaration does not identify which skills may require
authorization. A client discovers a concrete authorization request when a Task
enters `TASK_STATE_AUTH_REQUIRED`. The extension declaration is not an A2A
security requirement. A server MUST NOT add an Agent Card `securityScheme` or
`securityRequirement` solely because a skill uses this extension.

## Activation

A client activates this extension by including its URI in the
`A2A-Extensions` request header:

```http
A2A-Extensions: https://schemas.microsoft.com/agents/a2a/extensions/in-task-authorization/v1
```

The client MUST activate the extension on:

- The request that can initiate an in-task authorization flow.
- The corresponding `resumeAuth` request.

The server SHOULD echo the URI in the `A2A-Extensions` response header when the
extension was activated.

If a protected operation requires this extension but the initiating request
did not activate it, the server MUST NOT return extension-defined
authorization-request metadata. The server SHOULD reject the operation with an
unsupported-operation error that explains that extension activation is
required.

## Requesting authorization

When an agent requires an OAuth credential to continue an operation, it MUST:

1. Use a Task to track the operation.
2. Generate a cryptographically random authorization request ID.
3. Bind the authorization request ID to the Task ID, context ID, interrupted
   operation, and required authorization policy.
4. Transition the Task to `TASK_STATE_AUTH_REQUIRED`.
5. Include the authorization request object defined below in
   `TaskStatus.message.metadata`.

The server MUST retain enough state to correlate `resumeAuth` with the
interrupted operation. The server MUST NOT persist the procured credential as
part of that state.

### Authorization request metadata

The status message metadata key is the extension URI. Its value MUST contain an
`authorizationRequest` object.

```json
{
  "status": {
    "state": "TASK_STATE_AUTH_REQUIRED",
    "message": {
      "role": "ROLE_AGENT",
      "parts": [
        {
          "text": "Authorization is required to read the user's profile."
        }
      ],
      "metadata": {
        "https://schemas.microsoft.com/agents/a2a/extensions/in-task-authorization/v1": {
          "authorizationRequest": {
            "id": "f719ecb5c54a4e1d8b07c3091639fd80",
            "oauth2": {
              "flows": {
                "authorizationCode": {
                  "authorizationUrl": "https://login.example.com/oauth2/v2.0/authorize",
                  "tokenUrl": "https://login.example.com/oauth2/v2.0/token",
                  "scopes": {
                    "api://agent/access_as_user": "Access the agent as the signed-in user."
                  }
                }
              }
            },
            "requiredScopes": [
              "api://agent/access_as_user"
            ]
          }
        }
      }
    }
  }
}
```

The `authorizationRequest` object has the following fields:

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `id` | string | Yes | Cryptographically random, single-use authorization request ID. |
| `oauth2` | object | Yes | OAuth 2.0 security scheme information. |
| `oauth2.flows` | `OAuthFlows` | Yes | Exactly one OAuth flow the client can use to procure the credential. |
| `requiredScopes` | array of string | No | Scopes required for the interrupted operation. |

The OAuth flow scope dictionary describes scopes available from the
authorization server. `requiredScopes` describes the subset required by the
interrupted operation.

The server SHOULD also include a human-readable status message. It MUST NOT
place secrets, credentials, authorization codes, client secrets, or refresh
tokens in the status message or extension metadata.

## Delivering the credential

The client resolves the authorization request by:

1. Procuring a credential using the advertised OAuth flow.
2. Calling `resumeAuth` with the same Task ID and context ID as the interrupted
   request.
3. Providing the authorization request ID from the auth-required status.
4. Activating this extension with `A2A-Extensions`.
5. Sending the procured bearer credential in
   `A2A-InTask-Authorization`.

```http
Authorization: Bearer <endpoint-credential>
A2A-Extensions: https://schemas.microsoft.com/agents/a2a/extensions/in-task-authorization/v1
A2A-InTask-Authorization: Bearer <in-task-credential>
```

The endpoint credential and in-task credential MAY be the same value when the
credential satisfies both contracts. They remain logically distinct.

The server MUST NOT treat `A2A-InTask-Authorization` as a replacement for its
normal endpoint authentication.

## JSON-RPC binding

The JSON-RPC method name is `resumeAuth`.

```json
{
  "jsonrpc": "2.0",
  "id": "resume-1",
  "method": "resumeAuth",
  "params": {
    "taskId": "task-123",
    "contextId": "context-456",
    "authorizationRequestId": "f719ecb5c54a4e1d8b07c3091639fd80"
  }
}
```

The parameters are:

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `taskId` | string | Yes | ID of the Task in `TASK_STATE_AUTH_REQUIRED`. |
| `contextId` | string | Yes | Context ID from the original request. |
| `authorizationRequestId` | string | Yes | ID from the auth-required status metadata. |

On success, the result MUST be the latest Task. The operation SHOULD wait until
the resumed Task next reaches an interrupted or terminal state.

## HTTP/JSON binding

The HTTP/JSON operation is:

```http
POST /tasks/{taskId}:resumeAuth
```

The path is relative to the HTTP/JSON A2A interface URL.

```json
{
  "contextId": "context-456",
  "authorizationRequestId": "f719ecb5c54a4e1d8b07c3091639fd80"
}
```

The `taskId` path value, `contextId` body value, and
`authorizationRequestId` body value have the same semantics as the JSON-RPC
parameters.

On success, the response body MUST be the latest Task. The operation SHOULD
wait until the resumed Task next reaches an interrupted or terminal state.

## Server processing

Before resuming the interrupted operation, the server MUST verify:

- The extension was activated for the `resumeAuth` request.
- The Task exists and is in `TASK_STATE_AUTH_REQUIRED`.
- The Task ID and context ID match the stored authorization request.
- The authorization request ID matches and has not been consumed.
- The `A2A-InTask-Authorization` header contains exactly one Bearer credential.
- The credential is acceptable under the authorization policy associated with
  the interrupted operation.

The server MUST make the in-task credential available only to the resumed
operation. The server MUST NOT assume that it authorizes subsequent messages on
the Task.

The authorization request ID MUST be consumed at most once. The server SHOULD
consume it atomically with transition out of `TASK_STATE_AUTH_REQUIRED`.

After successful validation, the server:

1. Makes the in-task credential available to the interrupted operation.
2. Resumes that operation without requiring the client to resend the original
   A2A Message.
3. Emits normal Task status and artifact updates.
4. Returns the latest Task from `resumeAuth`.

The resumed operation MAY transition the Task to any state allowed by the A2A
Task state machine, including another `TASK_STATE_AUTH_REQUIRED` state for a
different authorization request.

## Error handling

The server MUST reject `resumeAuth` without resuming the operation when:

- Required parameters or headers are missing or malformed.
- The extension was not activated.
- The Task or authorization request is unknown.
- The Task ID, context ID, or authorization request ID does not match.
- The authorization request ID was already consumed.

These failures SHOULD use the binding's invalid-request, invalid-parameters,
task-not-found, unsupported-operation, or authorization error behavior as
appropriate. Error responses MUST NOT include the in-task credential.

If credential validation or an on-behalf-of exchange fails in a way that can be
corrected by procuring another credential, the server SHOULD leave the Task in
`TASK_STATE_AUTH_REQUIRED`, preserve the interrupted operation, and provide a
sanitized failure description. The client MAY retry `resumeAuth` with the same
authorization request ID until the server accepts a credential or invalidates
the request.

Canceling the Task MUST invalidate any outstanding authorization request and
MUST follow the normal A2A task-cancellation behavior.

## Security considerations

The `resumeAuth` operation delivers a bearer credential and MUST use TLS.

Servers and intermediaries:

- MUST NOT log the `A2A-InTask-Authorization` header.
- MUST NOT include the credential in Task history, status metadata, artifacts,
  traces, telemetry, or error responses.
- MUST NOT persist the credential unless a separate credential-management
  contract explicitly requires it.
- SHOULD redact the header using the same controls applied to the standard
  `Authorization` header.

Authorization request IDs MUST have enough entropy to resist guessing and MUST
be bound to the Task, context, interrupted operation, and authorization policy.
Possession of an authorization request ID alone is not a credential.

An implementation MAY validate the credential locally, exchange it
on-behalf-of the user, or pass it to the target resource that validates it.
The implementation MUST complete the configured authorization check before
performing the protected operation.

Clients SHOULD request the least privilege required by `requiredScopes`.
Servers MUST NOT infer authorization from the transition to
`TASK_STATE_AUTH_REQUIRED` itself.

## Complete example

### 1. Agent Card

```json
{
  "capabilities": {
    "extensions": [
      {
        "uri": "https://schemas.microsoft.com/agents/a2a/extensions/in-task-authorization/v1",
        "description": "Resolves task-scoped OAuth authorization requests.",
        "required": false,
        "params": {
          "operations": {
            "jsonRpc": "resumeAuth",
            "httpJson": "POST /tasks/{taskId}:resumeAuth"
          },
          "credentialHeader": "A2A-InTask-Authorization"
        }
      }
    ]
  },
  "skills": [
    {
      "id": "profile",
      "name": "Read user profile"
    }
  ]
}
```

### 2. Auth-required Task

```json
{
  "id": "task-123",
  "contextId": "context-456",
  "status": {
    "state": "TASK_STATE_AUTH_REQUIRED",
    "message": {
      "role": "ROLE_AGENT",
      "parts": [
        {
          "text": "Authorization is required to read the user's profile."
        }
      ],
      "metadata": {
        "https://schemas.microsoft.com/agents/a2a/extensions/in-task-authorization/v1": {
          "authorizationRequest": {
            "id": "f719ecb5c54a4e1d8b07c3091639fd80",
            "oauth2": {
              "flows": {
                "deviceCode": {
                  "deviceAuthorizationUrl": "https://login.example.com/oauth2/v2.0/devicecode",
                  "tokenUrl": "https://login.example.com/oauth2/v2.0/token",
                  "scopes": {
                    "api://agent/access_as_user": "Access the agent as the signed-in user."
                  }
                }
              }
            },
            "requiredScopes": [
              "api://agent/access_as_user"
            ]
          }
        }
      }
    }
  }
}
```

### 3. Resume request

```http
POST /a2a/tasks/task-123:resumeAuth HTTP/1.1
Host: agent.example
Authorization: Bearer <endpoint-credential>
A2A-Extensions: https://schemas.microsoft.com/agents/a2a/extensions/in-task-authorization/v1
A2A-InTask-Authorization: Bearer <in-task-credential>
Content-Type: application/json

{
  "contextId": "context-456",
  "authorizationRequestId": "f719ecb5c54a4e1d8b07c3091639fd80"
}
```

### 4. Resumed Task

```json
{
  "id": "task-123",
  "contextId": "context-456",
  "status": {
    "state": "TASK_STATE_COMPLETED",
    "message": {
      "role": "ROLE_AGENT",
      "parts": [
        {
          "text": "Name: Ada Lovelace"
        }
      ]
    }
  }
}
```
